## 二、报告分析

### 2.1 综合分析

本报告对 RK3576 开发板（fnOS）搭配 4×500GB HDD 的 ARM NAS 进行了系统性性能测试，覆盖计算、内存、存储、网络、协议、并发、稳定性、功耗八个维度，完成度 93.6%（73/78 用例）。

**总体性能画像**：RK3576 作为一款 8 核 ARM SoC（大小核架构，最高 2.2GHz），搭配 4 块机械硬盘和 1GbE 网卡，其性能瓶颈呈现出典型的"CPU 算力 + 机械盘 IOPS"双重受限特征。网络层本身可达线速的 94%，但经过协议封装和文件系统/RAID 层后，实际可用带宽大幅缩水——SMB 明文写仅 72.6MB/s、RAID6 本地顺序写仅 65.65MB/s，与千兆线速（125MB/s）之间存在巨大落差。

**瓶颈定位（逐层分析）**：

| 层级 | 实测吞吐 | 占线速比例 | 瓶颈判断 |
|---|---|---|---|
| 裸 TCP（iperf3） | 117.6 MB/s | 94% | 网络层几乎无瓶颈 |
| FTP 协议 | 107.5 MB/s | 86% | 轻量协议损耗小 |
| SMB 明文读 | 84.7 MB/s | 68% | 协议栈开销显著（约 28%） |
| SMB 明文写 | 72.6 MB/s | 58% | 协议+磁盘双重损耗 |
| RAID6 本地顺序写 | 65.65 MB/s | 53% | 核心瓶颈：HDD RAID6 写惩罚 |
| NFS 写 | 27.1 MB/s | 22% | NFS 同步写惩罚严重 |

对比链：本地卷(fio) → 协议(SMB/NFS/FTP) → 裸 TCP(iperf3) → 线速。从线速到 RAID6 本地写，累计损耗 47.5%，主要损耗发生在 RAID 层（奇偶校验写惩罚）和协议层（SMB 协议栈开销）；CPU 在写入时达到 56.5%，尚未打满，说明瓶颈在存储子系统而非纯算力。

**RAID 级别对比**：

| RAID 级别 | 顺序读 (MB/s) | 顺序写 (MB/s) | 4K 随机读 (IOPS) | 4K 随机写 (IOPS) |
|---|---|---|---|---|
| RAID0 | 237.9 | 287.52 | 375.1 | 1129.2 |
| RAID1 | 202.6 | 43.22 | 236.2 | 180.6 |
| RAID5 | 115.59 | 74.23 | 309.8 | 108.6 |
| RAID6 | 92.4 | 65.65 | 312.4 | 66.7 |
| RAID10 | 225.58 | 64.83 | 383.1 | 295.2 |

- **RAID0** 读写均为最优，适合性能优先、不关心冗余的场景；顺序写 287.52MB/s 甚至超过千兆线速（受益于条带化跨盘并发）。
- **RAID10** 读性能接近 RAID0（镜像可并行读），写性能仅为 RAID0 的 22.5%（需双写），但随机 IOPS 表现不俗。
- **RAID5/6** 受奇偶校验计算拖累，顺序写分别只有 74.23 和 65.65MB/s；RAID6 的 4K 随机写仅 66.7 IOPS，是 HDD 机械寻道 + 双校验计算的叠加结果。
- **RAID1** 顺序写最差（43.22MB/s），因需全盘镜像写入，4 盘 RAID1 相当于 4 倍写入放大。

**协议横向对比**：FTP 效率最高（107~109MB/s），WebDAV 次之（90~98MB/s），SMB 中等（72~85MB/s），NFS 写最差（27.1MB/s）。SMB seal 加密带来平均 24.6% 的性能损失，但得益于 aes-ce 硬件指令，未出现"腰斩"级退化（红旗未触发）。rsync over SSH 达到 88.2MB/s（含 SSH 加密开销），表现良好。

**并发扩展性**：写入拐点 N=4（聚合吞吐 95.5MB/s），读取拐点 N=8（聚合吞吐 108.3MB/s）。读取扩展性优于写入，说明读路径的内核锁竞争较轻；写入在 4 路后即饱和，瓶颈在 RAID 层的写带宽。

**稳定性与降频**：浸泡测试仅采集 4 个样本（≈2 分钟），数据不足以判断热降频趋势，S8-02 因样本过少而失败。从现有数据看，最高温度 63.8℃、CPU 频率稳定在 2112MHz，未见明显降频迹象，但需延长测试时间才能下结论。

**加密与压缩**：AES-128-GCM 硬件加速达到 1668.3MB/s（远超千兆线速），chacha20-poly1305 仅 406.7MB/s（纯软件），表明 aes-ce 驱动正常工作。pigz 压缩 54.7MB/s、解压 161.0MB/s，对于实时压缩场景够用。

**红旗信号检查**：四项 ARM 红旗信号均未触发——SMB 加密损失 24.6%（未腰斩），多流打满网卡时 CPU 未达 100%，长跑未检测到阶梯式下降，小文件 IOPS 未出现异常。这表明 aes-ce 硬件加密指令正常启用、中断亲和性配置合理、无明显热问题。

### 2.2 各指标含义

本报告涉及以下核心性能指标，理解其含义有助于正确解读测试数据：

**吞吐 (Throughput, MB/s)**
每秒传输的数据量（兆字节/秒）。顺序大块 I/O 关注此指标，反映存储或网络的带宽上限。数值越大越好。

**IOPS (Input/Output Operations Per Second)**
每秒完成的 I/O 操作次数。随机小块 I/O（如 4K）关注此指标，反映存储系统处理并发请求的能力。HDD 机械盘通常只有数百 IOPS，SSD 可达数万至数十万。

**延迟 (Latency, μs)**
单个 I/O 操作从发起到完成的时间（微秒，1ms = 1000μs）。P50 为中位数延迟（50% 的请求在此时间内完成），P99 为 99 分位延迟（仅 1% 的请求超过此值）。P99 反映长尾延迟，对数据库等延迟敏感型负载至关重要。P99 过高意味着存在偶发的严重卡顿。

**bs (Block Size, 块大小)**
每次 I/O 操作的数据块大小。1M 大块用于测试顺序带宽上限，4K 小块用于测试随机 IOPS 和延迟。机械盘大块顺序访问效率高，小块随机访问因寻道开销而性能骤降。

**QD (Queue Depth, 队列深度)**
同时等待处理的 I/O 请求数量。QD32 表示最多 32 个请求同时在队列中，用于压榨设备峰值性能；QD1 表示单请求队列，测出的延迟是单路径最低延迟。高 QD 可利用设备内部并行度提升吞吐，但也会增加延迟。

**jobs (numjobs, 并发作业数)**
同时运行的 fio 进程/线程数。多个 jobs 各自维持独立的 QD，总并发数 = QD × jobs。例如 QD32 × 4jobs = 128 路并发 I/O。多 jobs 可模拟多应用同时访问存储的场景。

**CPU% (设备整机 CPU 利用率)**
通过 `/proc/stat` 前后快照差值计算的设备整机 CPU 占用率，包含内核态（RAID 奇偶校验、文件系统、softirq、网络协议栈等）开销。用于判断算力是否先于存储/网络成为瓶颈。注意：这不是 fio 进程自身的 CPU 占用，而是整机利用率。

**direct=1 (直接 I/O)**
绕过操作系统的页缓存（page cache），直接与磁盘交互。使用 direct=1 且测试文件大于物理内存，可确保测到的是磁盘/RAID 真实性能，而非内存缓存"假象"。

**fsync 延迟**
每次写操作后调用 fsync() 强制将数据落盘（写入物理介质而非缓存）的延迟。这是数据库类应用（如 MySQL、PostgreSQL）的关键指标——它们每次事务提交都需要 fsync 保证持久性。fsync IOPS 低说明每次落盘提交代价高。

**裸盘读基线**
对 RAID 成员盘（/dev/sdX）直接做只读 fio 测试，得到的单盘原始性能。用于与 RAID 卷性能对比，计算文件系统层损耗和 RAID 效率。例如裸盘 126.96MB/s vs RAID6 92.4MB/s = 文件系统/RAID 层损耗约 27%。

**线速 (Line Rate)**
物理链路的理论最大带宽。1GbE 网卡的理论线速为 1000Mbps ≈ 125MB/s（含协议开销后实际可用约 118MB/s）。网络利用率 = 实测吞吐 ÷ 线速，是判断网络层是否瓶颈的核心指标。

**SMB seal (SMB 加密)**
SMB 3.x 协议的端到端加密功能。开启后数据在传输过程中加密，防止中间人窃听，但会增加 CPU 开销。加密损失 = (明文吞吐 - 密文吞吐) ÷ 明文吞吐 × 100%。ARM 平台依赖 aes-ce 硬件指令加速；损失超过 50% 通常意味着 AES 走了纯软件路径（红旗信号）。

**并发拐点**
吞吐不再随客户端/并发数增长而线性增长的转折点。拐点处的资源占用（CPU/网络/磁盘）即为系统瓶颈所在。例如写入拐点 N=4 意味着 4 个客户端同时写入后，再增加客户端也无法提升总吞吐。

**📖 测试方法(步骤)**

1. 设备端 fio,direct=1 直通存储(绕开页缓存),单 job 测试文件 4G(需大于物理内存,防止缓存作假);
2. 每个 profile 先热身 30s,再正式跑 3 轮取中位数,轮间波动 >10% 自动标记可信度下降;
3. 每轮 fio 前后对设备打 /proc/stat 快照,差值即该轮整机 CPU%(含内核态),多轮取中位数;
4. 7 个负载画像:顺序读/写(1M 大块)、4K 随机读/写、4K 混合读写 70/30、QD1 最低延迟、fsync 提交延迟;
5. S3-BASE-01 自动从 /proc/mdstat 识别 RAID 成员盘做只读裸盘基线,用于换算文件系统层损耗与 RAID 效率;
6. S3 分为 basic / RAID0 / RAID1 / RAID5 / RAID6 / RAID10 子组:人工切换阵列后运行对应组,执行前自动校验 /proc/mdstat 阵列级别,不符拒跑,防止数据串组。

**底层原理**

- direct=1 + 文件>内存,确保测的是磁盘/RAID 真实性能而非内存缓存;
- 1M 大块顺序 IO 反映带宽上限(受盘顺序速率与 RAID 条带/奇偶校验开销制约);4K 随机 IO 反映 IOPS 与延迟(受寻道/队列深度制约);
- iodepth×numjobs 把队列打满以逼出设备峰值;QD1 单队列给出最低延迟(单路径极限);fsync=1 测每次落盘提交延迟,是数据库类负载的关键指标;
- percentile(50/90/99/99.9)延迟用于暴露长尾;
- CPU% 口径为设备整机利用率(/proc/stat 前后差值,含 RAID 奇偶校验、文件系统内核线程、softirq 等内核态开销),用于判断算力是否先于存储成为瓶颈;fio 自报 CPU 仅为其进程自身占用,已另存 fio_proc_cpu_pct 供参考,不作为报告 CPU%。

**📖 测试方法(步骤)**
